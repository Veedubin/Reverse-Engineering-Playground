# v0.3.0 Proposal — Distroless + MCP Gateway Refactor

**Status:** Draft, awaiting approval
**Target version:** v0.3.0
**Author:** Boomerang-Orchestrator with user direction
**Created:** 2026-06-07

## Why

The v0.2.x line shipped a working multi-container stack (core, ghidra, radare2, filebrowser) and a working install path. But three architectural issues emerged during v0.2.x build-debugging that warrant a coordinated refactor in v0.3.0:

1. **All MCP servers run in the same container as OpenCode.** `opencode.json` lists 9 MCP servers; each one is launched as a local subprocess inside `re-core`. There is no isolation — if `revula` (which spawns angr/z3/yara subprocesses) OOMs, OpenCode's web server dies too. RAM is shared with no cgroup boundaries. A bad binary dropped into `/samples` that triggers a malicious or buggy tool can affect all 9 servers at once.

2. **No per-tool allowlists or call tracing.** Today every tool from every MCP server is always available. The agent could call `ghidra_decompile_function` *and* `yara_scan_with_rule` *and* `revula_disassemble_at_address` in the same session with no operator visibility. For a reverse-engineering tool that runs in LAN-exposed mode (LAN port 4096), an audit log of "what tool was called with what args at what time" is a basic security requirement that we don't have.

3. **Image sizes and rebuild cycles are bad.** `re-core` is ~800 MB because it ships Node.js 22 + Python 3.12 + .NET 9 + Wine + Mono + YARA + 200+ Python pip deps all in one Ubuntu 24.04 base. Every time we bump one of those, we rebuild the whole thing. The user pointed out that "why do we need node and python on the same image" is the right question — we don't, if we structure it differently.

## What we discovered

While researching this, the user pointed out **Docker's MCP Gateway** (https://github.com/docker/mcp-gateway, 1.4k stars, MIT-licensed, 68 releases). It's a centralized proxy that sits between AI clients and MCP servers, and it solves all three of the above problems natively:

- ✅ **Per-MCP-server containers** with cgroup resource limits (`--cpus`, `--memory`)
- ✅ **Per-tool allowlists** (`--enable <server>.<tool>`)
- ✅ **Built-in call tracing** (`--log-calls`)
- ✅ **Profile-based tool bundles** (e.g. load just `re-core` profile = revula + radare2; add `ghidra` profile = + ghidra-mcp; add `dotnet` profile = + ilspy-mcp)
- ✅ **Docker socket OR Podman socket** (works with our rootless podman-compose.yml if we mount `/var/run/podman.sock` instead of `/var/run/docker.sock`)
- ✅ **OCI-distributable catalogs** (our catalog becomes a YAML file you can `docker mcp catalog import`)
- ✅ **Secrets management** (`docker mcp secret` keeps API keys out of env vars)
- ✅ **Network policy** (`--block-network` per server)
- ✅ **OAuth flow handling** (for future MCPs that need browser-based auth)

## Goals (the v0.3.0 release)

1. **Decompose into ~6 tiny single-purpose containers**, each distroless-based:
   - `re-files` (FileBrowser) — already converted to distroless in v0.2.3
   - `re-core` (OpenCode web, Node.js 22) — distroless `nodejs22-debian13:nonroot`
   - `re-revula` (Python MCP server) — distroless `python3-debian13:nonroot`
   - `re-ghidra` (Ghidra SRE + bridge) — distroless `java21-debian13:nonroot` + `python3` stage
   - `re-radare2` (r2 + r2mcp + Wine) — distroless `cc-debian13:nonroot` + glibc + Wine stage
   - `re-ilspy` (.NET decompiler) — distroless `dotnet9-debian13:nonroot` (if available, else custom build)
2. **Add the Docker MCP Gateway as `re-broker`** in the compose stack. It manages all the MCP server containers and exposes a single MCP protocol endpoint to OpenCode.
3. **Replace `opencode.json` MCP config with a single gateway connection** (1 entry instead of 9).
4. **Define an OCI-distributable catalog** (`re-catalog.yaml`) listing all 9 MCP servers with their image refs, secrets, env vars, and tool allowlists.
5. **Use compose profiles** so users start only what they need:
   - `docker compose up -d` → starts `re-files` + `re-core` + `re-broker` (minimal RAM)
   - `docker compose --profile re up -d` → adds `re-revula` + `re-radare2`
   - `docker compose --profile ghidra up -d` → adds `re-ghidra` (saves 800 MB when not needed)
   - `docker compose --profile windows up -d` → adds `re-ilspy`
6. **Podman compatibility** maintained (mount podman socket instead of docker socket in `re-broker`).
7. **Call tracing + secrets management** enabled by default in the gateway.

## Non-goals

- We are NOT going to vendor the Docker MCP Gateway. We use it as a runtime dep, same as we use Ghidra or revula. (We could replace it with a self-built Go broker later if Podman support becomes a problem, but the project is MIT-licensed and active.)
- We are NOT going to drop the bare-metal install path (`./install.py`). Some users prefer no Docker at all. Both paths ship.
- We are NOT going to lock the user into Docker-only. Podman works as a drop-in for everything except the gateway, which needs a socket (and we use whatever the user has: `/var/run/docker.sock` or `/var/run/podman.sock`).
- We are NOT going to delete any of the 9 MCP servers. They all work. We're changing *how* they run, not *what* they do.

## Design

### New file layout

```
docker/
  core/         Dockerfile (Node 22 distroless)
  ghidra/       Dockerfile (Java 21 distroless + Python bridge stage)
  radare2/      Dockerfile (cc distroless + Wine stage)
  revula/       Dockerfile (python3 distroless + revula venv stage)
  ilspy/        Dockerfile (dotnet9 distroless)
  broker/       Dockerfile (uses docker/mcp-gateway image as-is)
  files/        Dockerfile (already distroless in v0.2.3)
catalogs/
  re-catalog.yaml    OCI-distributable catalog of all 9 MCP servers
docs/
  distroless.md      Reference: which distroless tag for which purpose
  mcp-gateway.md     Reference: how the broker works, how to extend
```

### Multi-stage build pattern (the key insight)

For each image, the pattern is: tiny distroless base + `COPY --from` from official upstream images. We do **not** build our own Python/Node/Java; we just copy what we need from `python:3.12-slim` or `node:22` or `eclipse-temurin:21`.

```dockerfile
# revula/Dockerfile — example
FROM python:3.12-slim AS build
RUN pip install --no-cache-dir --break-system-packages 'revula @ git+https://github.com/president-xd/revula.git@main[full]'
RUN pip install --no-cache-dir --break-system-packages --target=/install angr capstone lief

FROM gcr.io/distroless/python3-debian13:nonroot
COPY --from=build /install /usr/lib/python3/dist-packages
COPY --from=build /usr/local/lib/python3.12/site-packages/revula /usr/lib/python3/dist-packages/revula
# (or just COPY the whole /usr/local/lib/python3.12/site-packages/)
ENTRYPOINT ["python", "-m", "revula.server"]
```

This is the pattern from the Google `distroless/python3-requirements` example, applied to our needs.

### Broker integration

The `re-broker` service uses the official `docker/mcp-gateway` image. It reads the catalog at startup and spawns the MCP server containers on demand. OpenCode's `opencode.json` becomes:

```jsonc
{
  "mcp": {
    "gateway": {
      "type": "remote",
      "url": "http://re-broker:8080",
      "enabled": true
    }
  }
}
```

That's it. One entry. The gateway exposes 9×N tools to OpenCode as if they were all local.

### Catalog format

```yaml
# catalogs/re-catalog.yaml
name: reverse-engineering-playground
displayName: RE_Playground MCP Catalog
registry:
  revula:
    description: "All-in-one RE MCP server (PE/ELF/Mach-O, YARA, Capa, .NET IL, Frida, GDB)"
    title: "revula"
    type: "server"
    image: "ghcr.io/veedubin/re-playground/re-revula:latest"
    tools:
      - name: "binary_parse_pe"
      - name: "binary_parse_elf"
      # ... all 116 tools
  radare2-mcp:
    description: "Native r2 MCP server"
    title: "radare2-mcp"
    type: "server"
    image: "ghcr.io/veedubin/re-playground/re-radare2:latest"
  ghidra-mcp:
    description: "245-tool Ghidra MCP bridge"
    title: "ghidra-mcp"
    type: "server"
    image: "ghcr.io/veedubin/re-playground/re-ghidra:latest"
    profiles: ["ghidra"]  # only loaded with --profile ghidra
  # ... 6 more
```

### Compose profile structure

```yaml
# docker-compose.yml
services:
  files:
    profiles: [default]
    image: ghcr.io/.../re-files:0.3.0
    # ... exposed on :8080
  core:
    profiles: [default]
    image: ghcr.io/.../re-core:0.3.0
    # ... exposed on :4096
  broker:
    profiles: [default]
    image: docker/mcp-gateway:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock  # or podman.sock
      - ./catalogs/re-catalog.yaml:/etc/docker/mcp/catalog.yaml:ro
    # ... no exposed port; core talks to it via :re-broker:8080 on docker network
  revula:
    profiles: [re]  # opt-in
    image: ghcr.io/.../re-revula:0.3.0
  radare2:
    profiles: [re]
    image: ghcr.io/.../re-radare2:0.3.0
  ghidra:
    profiles: [ghidra]
    image: ghcr.io/.../re-ghidra:0.3.0
    # mem_limit: 4g, etc.
  ilspy:
    profiles: [windows]
    image: ghcr.io/.../re-ilspy:0.3.0
```

User commands:

```bash
# Minimal: just the web UI, file ingress, broker. ~150 MB RAM.
docker compose up -d

# Add the core RE tools. +500 MB.
docker compose --profile re up -d

# Add Ghidra. +800 MB.
docker compose --profile ghidra up -d

# Add .NET decompiler. +300 MB.
docker compose --profile windows up -d

# Stop everything (frees RAM, keeps volumes).
docker compose down
```

### Podman compatibility

For `podman-compose.yml`:

```yaml
services:
  broker:
    volumes:
      - /var/run/podman.sock:/var/run/podman.sock
    environment:
      DOCKER_MCP_IN_CONTAINER: "1"  # bypass Docker Desktop feature checks
```

The MCP Gateway is just a Go binary; it works with either socket if the socket protocol is compatible. (Docker's `/var/run/docker.sock` and Podman's `/var/run/podman.sock` are both Unix sockets speaking the Docker REST API; podman-pause compat mode makes them interchangeable.)

### CI changes

`.github/workflows/build-containers.yml` matrix expands from 4 services to 6 (adds `re-revula` and `re-ilspy`). Each service still gets 3 tags: `0.3.0`, `0.3`, `latest`. Layer caching via `cache-from: type=gha` already supports it.

`.github/workflows/validate.yml` updates:
- `install.py` syntax check (unchanged)
- All 6 Dockerfiles parse check (new)
- `re-catalog.yaml` YAML schema validation (new)
- `docker-compose.yml` profile validation (new)
- Existing checks: secrets, hardcoded paths, agent persona markers (unchanged)

## Migration path from v0.2.x

For existing users on v0.2.x:

1. `git pull` to get v0.3.0
2. Stop the old stack: `docker compose down`
3. Pull the new images: `docker compose pull` (or build locally: `docker compose build`)
4. Re-create the gateway catalog: `docker compose run --rm broker catalog import /etc/docker/mcp/catalog.yaml`
5. Start the new stack: `docker compose up -d` (default profile only)
6. Verify: visit `http://localhost:4096`, ask OpenCode to list MCP tools — should see all 9 server tool sets exposed as a single "gateway" tool list

We will keep the v0.2.x `docker-compose.yml` and `podman-compose.yml` working until v0.4.0 (a 2-release deprecation window).

## Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| MCP Gateway breaks on Ubuntu 24.04 / Podman 5 | Low | High | Test locally in this session before committing to refactor |
| Each distroless image is more complex to build than current `FROM ubuntu:24.04` | High | Medium | Build a working v0.3.0-pre1 first, validate locally, then promote |
| Removing `ghidra-mcp` from OpenCode config breaks existing user muscle memory | Low | Low | Document the change clearly; OpenCode's tool list just shows different names |
| Docker socket permission in rootless Podman | Medium | High | Document the workaround (`podman system service --time=0 unix:///var/run/podman.sock`); use userns_mode in compose |
| Total RAM exceeds user expectations | Medium | Low | Profile-based opt-in is the fix; document in README |
| Reverse-engineering-specific MCPs (revula's 116 tools) blow up tool count in OpenCode's system prompt | Medium | Medium | Use gateway's per-tool allowlists to surface only the most-used ~20 tools by default; advanced users enable the rest |
